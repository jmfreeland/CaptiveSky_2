# Editor render-budget check after Nanite Foliage restart

## Result

The main `CaptiveSky_2` project was reopened on `/Game/Maps/Island` in UE 5.8.3. The fresh editor startup log (`Saved/Logs/CaptiveSky_2.log`, 2026-10-29 03:19 UTC) sets `r.Nanite.Foliage:1` from project configuration, alongside `r.Nanite.ProjectEnabled:1`; this verifies the restart applied the project setting. The Island finished loading and the editor status bar showed **All Saved**.

An editor-viewport `stat streaming` observation showed a 4096 MiB pool capacity, a 3,726.57 MiB streaming pool (91%), and 629.55 MiB of wanted mips. There was no explicit over-budget banner in this editor view. This is not a PIE/Game pool measurement and does not contradict the user's recurring memory-exhaustion report. The startup log contains the landscape edit-layer warning: a 4033×4033 merge batch is needed while the current maximum is 1024×1024.

A read-only editor `ListTextures` dump at 03:34 UTC counted 636 textures (2,525.51 MiB in memory). It reports 1,637 MiB in `TEXTUREGROUP_RenderTarget` and 216 MiB in `TEXTUREGROUP_Terrain_Heightmap`; the render-target total is separate from the 4096 MiB streaming-pool figure and must not be added to or interpreted as streamed mips. The largest transient allocations were 4K targets: two 256 MiB `JumpFloodRT*` plus a 256 MiB `WaterDepthAndVelocityRT`, two 128 MiB `CombinedVelocityAndHeightRT*`, and a 128 MiB `DepthAndShapeRT`. The installed UE Water editor-plugin header declares these as transient `WaterBrushManager` render targets. The same dump lists five 64 MiB `ScratchLandscapeRT2D` targets, two 64 MiB heightmap targets, and two 16 MiB weightmap targets. This makes the editor's Water/Landscape brush buffers a concrete memory investigation lead, but does not establish their peak allocation in PIE or prove they caused the earlier memory warning. The engine installation lacks the plugin implementation `.cpp`, so the exact sizing path is not verified; do not change the project/editor water resolution based on this snapshot alone.

A whole-device `nvidia-smi` sample at 03:19 UTC reported 6,539 / 12,282 MiB GPU memory used, 5,459 MiB free, and 0% utilization. A later sample at 03:39 UTC showed 9,179 / 12,282 MiB used, 52% utilization, and 77°C. WDDM exposed no running per-process rows, so neither reading attributes the memory or activity to Unreal. With only about 3 GiB free in the later sample and a prior runtime preview ending with a Windows memory-pressure toast, no PIE/Standalone test was started.

A further whole-GPU sample at 03:47 UTC showed 9,691 / 12,282 MiB used, 39% utilization, and 74°C; WDDM still listed no per-process GPU rows. Task Manager's process list showed UnrealEditor at roughly 6,190 MiB of system RAM and near-idle CPU on refresh, but the GPU columns were not available in that observation. This does not identify the GPU allocation. The available headroom remained too low to start PIE safely.

## Limits and next step

No PIE/Standalone session was started in this check. There is no new evidence for gameplay FPS, p95 frame time, peak Unreal VRAM, water traversal, or Nanite assembly visual equivalence/performance. Do not infer that Nanite Foliage fixed performance from CVar activation or the editor viewport.

Next, identify what is driving the un-attributed WDDM GPU use, then repeat `ListTextures` after a clean editor restart and check whether the Water/Landscape editor targets are still resident without an edit/build operation. Compare any isolated runtime's `stat streaming` with its total RHI/GPU memory rather than conflating them. Investigate the existing `M_Island_Textured_Wet` invalid texture index with the landscape-material owner. Only run a matched frame-time/peak-memory A/B when the editor is closed and sufficient GPU headroom is available; keep the real-time and model-request caps explicit and low.
